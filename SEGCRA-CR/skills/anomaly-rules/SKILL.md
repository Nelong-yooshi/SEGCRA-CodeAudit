# 異常交易規則審查要點

> ⚠️ 通用佔位版:實際規則語意需依導入單位的核定規格補齊。以下為通用模式。

異常交易規則 SQL 的典型結構:**時間窗 + 聚合 + 閾值比較**,三個部位都是誤寫熱區。

## 時間窗
- 邊界:`>= start AND < end` 才是半開區間;`BETWEEN` 會把邊界重複計入相鄰窗
- 滾動窗 vs 日曆窗混用(近 24 小時 ≠ 當日)
- 批次執行時間假設:規則在 T+1 跑,時間窗卻寫 `SYSDATE`

## 聚合
- 粒度錯誤:應按「帳戶+日」聚合卻按「交易」聚合,或反之
- 沖正/退匯:金額聚合規則若看不到沖正/退匯的處理(排除或反向沖抵),
  **必須以 info 級 finding 提問**確認資料是否已於前置系統淨額;
  但團隊慣例(conventions)若已註明資料已淨額,則不要提出
- 重複入帳(同一交易多筆流水)未去重
- 通報粒度:規則 JOIN 會員/卡片等一對多資料表時,GROUP BY 若含帳戶以外的識別欄位,
  聯名戶等多紀錄情形會產生重複通報;通報應以帳戶(或規則主體)為唯一粒度。
  **這會讓同一帳戶被通報多筆(結果算錯)→ 至少 major,不可標 info/minor**;
  正確寫法是只 `GROUP BY account_id`,會員欄位用 `MAX()`/子查詢取回
- 幣別未過濾或未換算就 SUM

## 閾值比較
- 閾值 magic number 未對應規則編號/核定依據 → 要求註記來源
- `>` vs `>=` 與規則文字不一致
- NULL 帳號/NULL 金額被聚合吃掉(COUNT(col) vs COUNT(*))

## 誤報面
- 規則是否會掃到內部測試帳戶、批次代付等已知豁免清單?豁免邏輯用 NOT IN 時注意 NULL 陷阱

審查此類 MR 時,對每個規則變更問一句:**這個改動會讓哪些原本命中的交易不再命中(漏報),
哪些原本不命中的開始命中(誤報)?** 把答案寫進 finding 的 detail。
