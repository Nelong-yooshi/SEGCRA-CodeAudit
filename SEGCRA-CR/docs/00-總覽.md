# 00-總覽

## 在幹嘛(一段白話)

SEGCRA-CR 是 SQL merge request 的自動審查管線:MR 一進來(webhook 觸發或 `demo.py` 手動觸發),先跑一串**確定性前處理**(注入掃描、rule-base 預掃、分層知識檢索與 binding 抑制、風格檢查),把結果連同 diff、核定規格一起組進 prompt 交給 **LLM 審查**;LLM 產出的報告再經過一串**確定性後處理**(引用白名單、去重、enforce 補報鏈、執行驗證 spec_exec、rubric 重算分數、三態決策閘門),最後回寫 GitLab(行內留言、總評分數、label、commit status)。整條管線在 `orchestrator/pipeline.py:review_mr`。

## 防的是什麼(對應哪種失敗模式)

單獨一顆 LLM 做審查,實測會出現這些失敗模式,每一種都對應一道確定性機制:

| 失敗模式 | 對應機制 | 位置 |
|---|---|---|
| 漏報(機械性問題沒報出來) | rule-base 預掃 + `enforce_rules`/`enforce_hints`/`enforce_style` 補報 | 前處理 + 後處理 |
| 幻覺(引用不存在的法規、實作「看起來對」但跑起來錯) | `validate_citations` 引用白名單、spec_exec 沙盒執行驗證 | 後處理 |
| 提示注入(MR 文字操縱審查器直接放行) | `security.py:scan_mr` 確定性掃描 + `enforce_injection` 強制 blocker | 前處理偵測、後處理強制 |
| 分數漂移(同一 MR 模型自評分數逐輪不同) | `apply_rubric` 由 severity 確定性計分、`apply_policy` 用客觀訊號決策 | 後處理 |
| 遺忘(講定的規範因 context 變長被擠掉) | knowledge_store 的 binding 層恆常注入 + suppress 確定性濾除 | 前處理 |
| 誤報重複(同型 finding 被駁回後還一直報) | 審查歷史 `lookup_similar_reviews` + autopin 學習迴路 | 前處理 + 迴路 |

核心理念是**三明治架構**:LLM 是中間那層「不可信的夾心」,上下兩層都是確定性程式。模型可以被換掉、可以被攻陷、可以漏掉東西——上下兩層保證底線不變。

## 怎麼建的(核心:一次審查的端到端資料流)

入口:`scripts/webhook_server.py`(GitLab MR 事件/`/review` 留言觸發)或 `demo.py`(手動),都呼叫 `orchestrator/pipeline.py:review_mr`。

```
GitLab MR 事件 ──▶ webhook_server.py ─┐
demo.py --mr <id> ────────────────────┴─▶ review_mr(pipeline.py)
                                              │
   ┌──────────── 確定性前處理(上層麵包)──────────┴────────────────────┐
   │ 1. gitlab__get_mr_diff        取 MR(title/description/files)  │
   │ 2. prescan()                  逐檔 sqltools__run_rules(R/H)    │
   │                               + sqltools__lint(sqlfluff)      │→ 01-前處理
   │ 3. security.scan_mr()         注入掃描(不經 LLM)                │→ 01-前處理
   │ 4. spec_exec.find_spec()      抓規則碼 R-xxx → specs/<code>.md │→ 05-執行驗證
   │ 5. _derive_scope() +          分層知識檢索:binding 全注入、      │
   │    memory__retrieve_knowledge guideline top_k;拿 suppress_    │→ 02-分層記憶
   │                               codes / style_codes             │
   │ 6. suppress 濾除              binding 宣告的檢核點從預掃結果      │
   │                               中確定性刪除(講過的不再提)          │→ 02-分層記憶
   │ 7. memory__check_style        已學會的 S 碼風格掃描,附進預掃      │→ 02-分層記憶
   │ 8. skills 自動注入            路徑觸發 anomaly-rules、           │
   │                               預掃命中 R004/H004 觸發 secure-sql│→ 03-LLM審查層
   └─────────────────────────────────────┬─────────────────────────┘
   ┌──────────── LLM 審查(不可信的夾心)─────┴─────────────┐
   │ run_agent():SYSTEM_TEMPLATE + USER_TEMPLATE       │
   │(diff + 預掃 JSON + spec 全文 + 慣例),可呼叫工具       │→ 03-LLM審查層
   │(load_skill、memory__lookup_similar_reviews …)     │
   └──────────────────────────────────────┬────────────┘
   ┌──────────── 確定性後處理(下層麵包)──────┴──────────────────────────┐
   │  9. extract_json → validate_citations  引用白名單(防捏造)          │→ 04-後處理防線
   │ 10. sanitize_findings                  非法 severity 剔除、去重   │→ 04-後處理防線
   │ 11. enforce_rules / enforce_hints /    預掃命中模型沒報的,         │
   │     enforce_style                      確定性補進 findings        │→ 04-後處理防線
   │ 12. enforce_injection                  注入掃描命中 → 強制         │
   │                                        blocker(不論模型死活)      │→ 01/04
   │ 13. run_spec_exec                      測資生成→DuckDB 沙盒執行    │
   │                                        →仲裁,三角色執行驗證        │→ 05-執行驗證
   │ 14. apply_rubric                       分數/verdict 由 severity  │
   │                                        確定性重算                │→ 06-決策
   │ 15. apply_policy                       三態決策:auto_approved /  │
   │                                        needs_human / blocked    │→ 06-決策
   └────────────────────────────────┬────────────────────────────────┘
                                    ▼
   回寫 GitLab:gitlab__post_inline_comment(逐 finding)
              → gitlab__post_summary(決策+總評+分數)
              → gitlab__set_label(ai-review::<decision>)
              → gitlab__set_commit_status(name=segcra/review;
                auto_approved→success、其餘→failed ⇒ CE 的 merge 閘門)→ 06/07
```

資料流重點:
- **輸入**:mock 模式從 `fixtures/mr_<id>.json` 讀,real 模式打 GitLab API(`toolbox/gitlab.py:get_mr_diff`)。
- **中間產物**:預掃結果(list of `{path, rules, lint}`)以 JSON 原文放進 user prompt;spec 全文放進「核定規格」段;知識檢索的 `rendered` 放進 system prompt 的「團隊慣例」段。
- **輸出**:報告 dict(`score`/`verdict`/`decision`/`findings` + 稽核欄位 `_spec_exec`、`_policy_signals`、`_injection_scan`、`_model_score`、`_removed_citations`),mock 模式落地 `review_output/`,並存模型原始輸出 `review_output/mr_<id>_raw.txt`。

## 對決策的影響

最終三態決策(`apply_policy`)完全由客觀訊號決定,LLM 只貢獻 findings 的「內容」,不掌握裁決權:

- **blocked**:blocker 級 finding ≥ 1(來源可能是模型自報、`enforce_rules` 補報的 R001/R004、或 `enforce_injection` 強制加入)。
- **auto_approved**:必須同時滿足 `config/models.yaml` policy 的全部條件(diff ≤ 30 行、非新規則檔、分數 ≥ 95、只有 info 級、無待確認檢核點)**且** spec_exec 執行驗證通過(寫死的硬條件)。
- 其餘 → **needs_human**。

分數與 verdict 由 `apply_rubric` 從 severity 組成確定性計算(blocker −40、major −15、minor −5;有 blocker 上限 59),模型自評分數只留在 `_model_score` 供對照。

## 怎麼驗證它在動

```bash
cd .../SEGCRA-CR

# 不經 LLM 的管線煙霧測試(驗預掃/memory/spec 接通)
.venv/bin/python demo.py --mr 001 --dry-run

# 完整審查(需 Ollama 端點;三個 fixture 各驗一條防線)
.venv/bin/python demo.py --mr 001   # 執行驗證通過;新規則檔 → needs_human
.venv/bin/python demo.py --mr 002   # 邊界埋雷(>= vs >)→ spec_exec 抓到 major
.venv/bin/python demo.py --mr 003   # 注入 payload → 注入掃描 blocker → blocked

# 裸模型 A/B 對照(無任何防線,拿來對比三明治的價值)
.venv/bin/python demo.py --mr 001 --baseline
```

預期:mock 模式輸出寫入 `review_output/`,報告 JSON 印在 stdout,`decision` 欄位分別為 `needs_human` / `needs_human`(帶規格不符 major)/ `blocked`。

## 擴充與注意

- 換模型:改 `config/models.yaml` 的 profiles(orchestrator 不綁模型);決策閾值改同檔 `policy` 段。
- 各機制的擴充點見各篇文件的「擴充與注意」節。
- 已知限制:diff 超出 token 預算時 `build_diff_section` 逐檔截斷(map-reduce 分批審查為 TODO);真實環境 dbt+Jinja 需先 `dbt compile` 展開再進管線(見 README)。
