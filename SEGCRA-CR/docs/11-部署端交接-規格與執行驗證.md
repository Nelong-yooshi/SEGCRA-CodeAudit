# 11-部署端交接:規格放哪、執行驗證怎麼跑

這一篇給**在部署端操作這套工具的人**:規格檔要放在哪、要寫到什麼程度才驗得起來、
沙盒怎麼起停、一次審查跑完要去哪裡看執行驗證的結果、失敗時先查什麼。

機制本身的細節在 [05-執行驗證spec_exec.md](05-執行驗證spec_exec.md);可以設定的參數
只列在 [10-設定參數.md](10-設定參數.md) 一個地方,這裡不重複,只說哪一項會影響你。

---

## 1. 規格檔放哪

執行驗證的真值來源是**你們 repo 裡的規格檔**,不是這包工具附的那幾份。

| 項目 | 規定 |
|---|---|
| 路徑 | repo 根目錄下的 `specs/<規則碼>.md`,例如 `specs/R-093.md` |
| 規則碼 | `R-` 加 2–4 位數字(`R-93` 與 `R-093` 是不同的檔名,要跟 MR 裡寫的一致) |
| 內容開頭 | 第一個字元必須是 `#`。取回的內容不以 `#` 開頭時一律當成「沒拿到」—— GitLab 對沒有權限的檔案回的是 404 頁面,那種內容不能當規格用 |
| 讀的是哪一版 | **這次 MR 的那一版**(審查一開始就釘住 head commit)。所以規格與 SQL 可以在同一個 MR 裡一起改,驗證用的是改後的規格 |

**MR 要讓工具找得到規則碼**:工具從 MR 的標題、描述、每個檔案的路徑與內容裡找
`R-xxxx`。三個地方都沒出現的話,就是「無規格可驗」。

找不到規格不會靜默跳過,一律是 major finding、不得自動放行:

| 報告上的 finding | 意思 |
|---|---|
| 無規格可驗,無法執行驗證 | MR 裡找不到任何 `R-xxxx` |
| 執行驗證沒有完成:取不到規格 | 找到規則碼,但 `specs/<碼>.md` 取不回來。finding 裡附一個代碼(`not_found`、`no_read_token`、`not_a_spec`…),照 [10 篇](10-設定參數.md) 最後那張表查 |

> 這包工具自己的 `specs/` 只是離線開發與評測用的樣本。真實模式**不讀它**,一律去
> GitLab 取 —— 否則 MR 改了規格,驗證拿到的還是樣本那份,而報告上看不出來。

---

## 2. 規格要寫到什麼程度

測資是照規格生出來的:規格沒寫清楚的部分,生出來的測資就不會去測,報告上會出現
「覆蓋缺口」。**可判定**是唯一的要求 —— 每一條都要能翻成一句 SQL 判斷式。

一份驗得起來的規格要有這幾段(本包 `specs/R-093.md` 可以當格式範例):

| 段 | 為什麼需要 |
|---|---|
| 資料表定義(`CREATE TABLE`) | 沙盒照它建表。沒有這段就只能靠模型猜欄位名與型別,猜錯整次驗證報廢 |
| 交易範圍 | 哪些列算在內(`tx_type = 'TRANSFER'`、分不分通路/幣別) |
| 聚合方式 | 以什麼為單位、算什麼(每帳戶每日 `COUNT(*)`) |
| 閾值**含不含** | 「達 20 筆」要寫成 `>= 20`,並寫明 19 筆不通報。含不含等號是靜態審查最容易看漏、而邊界測資一跑就現形的那一類錯 |
| 時間窗 | 半開區間還是閉區間(`>= @start_date AND < @end_date`),涵蓋的是哪一段 |
| 豁免 | 沒有就寫「無」。空白會被當成「沒寫」而產生覆蓋缺口 |
| 通報粒度 | 每帳戶每日至多一筆?重複通報算不算錯? |
| 輸出欄位 | 欄位名與意義 |

**用字**:「達」、「含」、「以上」這類詞要在規格裡自己換算成運算子;寫「金額大於
十萬」而沒說含不含,驗證只能照一種解讀跑,另一種就成了沒驗到的缺口。

## 3. 沙盒(執行驗證要連的資料庫)

規則程式跑在 MS SQL 上,驗證就必須在同一種引擎上跑 —— 型別轉換、日期運算、NULL
處理的細節不一樣,換引擎驗出來的「通過」不能代表正式環境(README 的 ADR-01)。

- **起停**:`scripts/sandbox.sh start | stop | status`。一次性容器,沒有掛資料卷
  (停掉資料就沒了),只綁 `127.0.0.1`、不對外。SQL Server 常駐約吃 2GB 記憶體,
  **用完請 stop**。
- **權限**:跑這支腳本的帳號要能操作 docker。不給一般帳號 docker 權限的話,請維運
  包一個只能 start/stop/status 的指令出來(我們自己的伺服器就是這樣做的)。
- **設定**:密碼等參數放 `config/sandbox.env`(不進版控,範本是
  `config/sandbox.env.example`)。`SANDBOX_MSSQL_PASSWORD` 沒設 = 連不上沙盒 =
  執行驗證一律「無法完成」、不得自動放行。
- **確認通了**:`scripts/sandbox.sh status` 要出現「執行中、可連線」。容器在跑但連
  不上通常是還在啟動(第一次約 20–40 秒)。

每次審查在沙盒裡建一個**專用資料庫**(同時進行的審查互不干擾),每個案例在獨立交易裡
建表、灌資料、執行 MR 的 SQL,結束一律 rollback,整段跑完刪掉那個資料庫 —— 審查之間
不留狀態。

## 4. 跑完去哪裡看

**MR 上**看到的是 finding:

| finding | 意思 |
|---|---|
| 執行驗證:N 個生成測試案例皆符合預期(info) | 通過。文字本身會寫明「測資與驗證出自模型,AI 可能有幻覺」—— 它不是形式證明 |
| 執行驗證失敗:實作與規格行為不符(major) | 仲裁判定是 SQL 的問題,不是測資造錯 |
| 執行驗證覆蓋缺口(info) | 有條件沒被兩向(成立/不成立)測到,那部分沒驗 |
| 執行驗證無法完成(測資生成失敗 / 沙盒不可用 / 測資無法建置)(major) | 三種的修法不同:調 prompt、看沙盒環境、看規格的建表段 |
| 執行驗證:SQL 無法在測資上執行(major) | SQL 在沙盒編譯或執行不過 |

**報告檔**(`REVIEW_OUTPUT` 底下的 json)裡 `_spec_exec` 是完整結果:

| 欄位 | 內容 |
|---|---|
| `passed` | 這次執行驗證通不通過。**自動放行的硬條件**:有效案例要存在、沒有仲裁判成 SQL 錯的案例、沒有覆蓋缺口 |
| `spec_code` / `executed_file` | 驗的是哪份規格、哪個檔案 |
| `conditions` | 規格被拆成的原子條件 |
| `case_results` | 逐案結果(預期命中與否、實際命中與否) |
| `coverage_gaps` | 沒被兩向測到的條件;沙盒逾時沒跑完的案例也記在這裡,而且會寫明是逾時 |
| `dropped_cases` | 仲裁判定是測資造錯而剔除的案例 |
| `label_unverified` | 標籤沒驗到的案例:資料灌進去了、SQL 也跑了,但無法確認那筆資料真的測到它宣稱的那一條。這些**不算覆蓋缺口**,但「皆符合預期」那句話的證明力會因此小很多,所以 finding 裡會附一句 |
| `engine` / `stage_seconds` | 連到的引擎、三個階段各花幾秒 |

## 5. 失敗時先查什麼

| 症狀 | 先查 |
|---|---|
| 每個 MR 都「無規格可驗」 | MR 標題/描述/檔案裡有沒有 `R-xxxx`;規則碼的位數跟檔名對不對得上 |
| 「取不到規格」且代碼是 `not_found` | `GITLAB_PROJECT`、token 對這個專案的權限(**沒權限時 GitLab 回 404 不是 403**)、`specs/` 的路徑 |
| 「取不到規格」且代碼是 `not_a_spec` | 那個檔案被改壞了或放錯位置。這一個不是環境問題,要看 repo |
| 「沙盒不可用」 | `scripts/sandbox.sh status`;`config/sandbox.env` 的密碼;port 有沒有被佔 |
| 「測資無法建置」 | 規格的 `CREATE TABLE` 那段:欄位名、型別、是不是 T-SQL |
| 一直「覆蓋缺口」 | 規格裡那一條是不是沒寫成可判定的形式(含不含等號、豁免寫不寫「無」) |
| 每個案例都 `label_unverified` | 判斷式(`check_sql`)算不出來。先看 `_spec_exec.label_unverified` 裡的原因 |
| 執行驗證整段逾時 | `SPEC_EXEC_TIMEOUT_SECONDS`,以及離整份審查截止還剩多少時間(見 [10 篇](10-設定參數.md)) |

## 6. 交接邊界

| 誰 | 負責什麼 |
|---|---|
| 規則/業務端 | `specs/*.md` 的內容與維護:規格是驗證的唯一真值,規格沒寫清楚的部分沒有人能幫它補 |
| 維運 | 沙盒的起停與資源、`config/*.env`、GitLab token 與 webhook、時間上限的調整 |
| 工具端 | 三個角色(測資生成、沙盒執行、仲裁)的行為,以及報告欄位的意義 |

**規格與 SQL 改在同一個 MR 裡**是預期用法:驗證讀的是這次 MR 的規格版本,所以「改
規格 + 改實作」會用改後的規格去驗改後的 SQL。
