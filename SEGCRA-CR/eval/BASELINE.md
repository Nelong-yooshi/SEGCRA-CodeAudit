# baseline 方法書 — 在管線層不可重現的系統上量出可信的數字

這份文件定義 SEGCRA-CR 的 baseline **怎麼建、怎麼判讀、什麼情況下不准互比**。
它是流程本身,不是某一次的結果;某一次的結果在 `eval/baselines/<日期>-<sha>/REPORT.md`,
目前的實測現況在 [README.md](README.md)。

工具:
- `eval/preflight.py` — 起飛前檢查與環境指紋
- `eval/run_baseline.py` — 跑批、分級、彙總、回歸判定
- `eval/run_eval.py` — 單輪評測(`--dump-reports` / `--from-reports` 把收集與評分拆開)

---

## 0. 一句話結論

**同一份程式碼、同一個環境,跑兩次結果不一定一樣。所以 baseline 不是一組數字,
而是一組「數字 + 那個數字晃多少」。** 本文件其餘部分都是這句話的推論。

---

## 1. 問題:baseline 同時被要求做三件不同的事

| 用途 | 要回答的問題 | 需要什麼 |
|---|---|---|
| A. 回歸閘門 | 「我這次改動有沒有讓事情變糟?」 | **辨別得出訊號與噪音** |
| B. 能力報告 | 「這個系統到底有多準?」 | **代表性**與誠實的絕對水準 |
| C. 驗收證據 | 給甲方看「它真的有用」 | 可信、可複述 |

issue #8 §4 訂的方針是「回歸比較固定 temperature 0 + 固定 seed 求可重現;
能力報告保留隨機性、跑多次報分布」。這是**兩種模式**,而兩種都已經實作了:

| | `temperature` | `seed` | 由誰決定 |
|---|---|---|---|
| **正式審查** | 0.1 | 不帶 | `config/models.yaml` |
| **量測(跑批)** | 0 | 42 | `eval/run_eval.py` 用 `os.environ.setdefault` 帶預設 |

分成兩層是刻意的:`models.yaml` 是**共用設定**,webhook 正式審查與 `demo.py` 都讀它,
把固定值寫在那裡會連正式審查也變成 temperature 0(這正是 PR #9 review 指出並修掉的)。
改成由 `run_eval.py` 帶預設之後,固定值只在跑批時生效,而且 `setdefault` 讓呼叫端
明確設的環境變數優先(`LLM_SEED=` 空字串就是取消固定 seed,出能力報告時用)。

**`run_baseline.py` 是透過 `run_eval.py` 跑每個 case 的**,所以跑批自動吃到這組預設,
不需要額外做什麼。

> **但本分支目前還沒有那一段。** 量測模式的三個 commit(`ModelProfile.seed`、
> `config.py` 讀 `LLM_TEMPERATURE`/`LLM_SEED`、`run_eval.py` 帶預設)都在 PR #9 上,
> 還沒合進來。在 #9 合併之前,在本分支上跑批用的是**正式審查那組設定**(0.1、無 seed),
> 指紋的 `params.seed_sent` 會記下這件事,不要拿那種跑批去跟合併後的互比。

先看實測。這幾列是雙方獨立驗過、結論一致的:

| 實驗 | 設定 | 結果 |
|---|---|---|
| 短 prompt,模型端點,**明確帶 seed** 兩次 | temp=1.0, seed=42 | ✅ **逐字相同** |
| 同上,**不帶 seed** 的對照組兩次 | temp=1.0, 無 seed | ✅ 兩次不同(證明這個 prompt 本來有隨機空間,上一列不是假陽性) |
| R-201 測資生成跨天重跑 | temp=0, seed 固定 | ✅ 產出的 token 數完全相同 |
| `mr_406` **整條管線**背靠背兩次 | temp=0, seed=42 | ⚠ spec_exec 數字相同,但報告文字不同、finding 數 1 vs 3 |
| `mr_406` **整條管線**跨 6 小時 | temp=0, seed=42 | ❌ 翻盤:18 案例/0 缺口/通過 → 11 案例/5 缺口/不通過 |

**關鍵在最後兩列:那兩次跑批是有帶 seed 的,還是翻盤了。** 所以「固定 seed」
並不足以讓整條管線可重現——這是本方法書存在的理由,也是它不能被
「seed 有生效啊」一句話取消的原因。

> **為什麼帶了 seed 還會飄,尚未證實。** 最可能的解釋是管線是多輪 agent loop,
> 後一輪送出去的 prompt 含前一輪的工具結果,而那裡面有會變的東西(每次新建的
> 隨機沙盒資料庫名、執行錯誤訊息的內容、各層回傳的排序)。**輸入一變,
> 同一個 seed 也救不了**——seed 固定的是「同輸入下的取樣」,不是「輸入」。
> 驗法在 §7 的 `--dump-prompts`:把 `mr_406` 兩次實際送出的 prompt 存下來 diff,
> prompt 相同 → 是取樣;prompt 不同 → 是輸入,而且 diff 直接指出是哪一段在變。
> 第二種是可以逐項修掉的,修掉噪音就會跟著降。

**更正紀錄**:本文件先前版本寫「`models.yaml` 的 `seed: 42` 被模型端點接受但忽略,
所以我們沒有任何取得可重現結果的機制」。**那是錯的**:端點沒有忽略 seed,帶了就生效
(上表前兩列,雙方各自驗過)。錯的來源是看到管線跨時段翻盤,就替它編了一個根因,
而沒有去看管線實際送出去什麼。真正的情況是**帶了 seed 也還是會翻盤**,
原因在輸入端而不在取樣端。

結論:**A(回歸閘門)不能只靠「固定 seed」來建立。** 方法不變——本文件其餘設計
都是為了在「已經固定了 seed、但仍然會飄」的前提下做到 A,那些設計此刻依然成立。
正式模式的設定。方法不變——本文件其餘設計都是為了在這個前提下仍然做得到 A。
其餘設計都是為了在這個前提下仍然做得到 A,那些設計此刻依然成立。

### 為什麼「跑三次取平均」也不夠

平均會把最關鍵的資訊丟掉:**哪些案例本來就穩、哪些本來就會晃。**
把 `mr_601`(每次都 15 案例)和 `mr_406`(18/0 ↔ 11/5 跳動)平均在一起,
等於用同一把尺量兩種東西。而我們要判斷回歸,需要的恰恰是「這個 case 晃多少」。

## 2. 核心原則:先量噪音,再量品質

**沒有人量過「什麼都不改時,數字會晃多少」。** 我們只有 `mr_406` 翻盤這一個軼事。
不知道噪音有多大,就無法判斷任何差異是改壞了、還是它本來就會晃。

所以分兩階段。

### 階段一:噪音基線(measure the instrument)

```bash
python eval/run_baseline.py --stage1 --runs 5 --tag noise
```

同一份程式碼、同一個環境,每個 case 連續跑 5 次。**這不是品質量測**,
是量「測量工具本身的抖動」。每個 case 產出:

```
mr_406: 通過 2/5 | 執行驗證案例數 [18,11,11,16,11] | 覆蓋缺口 [0,5,5,2,5] | 決策 needs_human×5
```

依結果分三級。判準寫在 `run_baseline.py` 的 `grade()`,不散在程式各處——
**改門檻等於改方法**,改了就要回來更新這份文件並重跑階段一。

| 等級 | 判準 | 後續怎麼用 |
|---|---|---|
| **穩定** | N 次的**判定**與**數值**全部一致 | 單跑一次就有意義;翻盤即視為回歸,**可當硬閘門** |
| **邊界** | 有變動,但覆蓋缺口極差 ≤ 2 且案例數極差 ≤ 3 | 只看分布位移,**不當硬閘門** |
| **不穩** | 數值大幅跳動 | 只當觀測指標;先修測資生成,修好前**不列入評分** |

觀測值刻意分成兩軸,因為它們的用途不同:

- **判定**(斷言過不過、決策落在哪、執行驗證通不通)→ 決定能不能當閘門
- **數值**(驗了幾案、缺幾角、抓到幾條、誤報幾條)→ 決定數字能不能比 delta

有的 case 判定每次一樣但數值會晃——那還能當閘門,只是不能拿它的數字比 delta。
合成單一等級會把這件事蓋掉,所以 `summary.json` 兩軸都留。

> **這張分級表本身就是交付物。** 它直接回答「這套測試能信到什麼程度」,
> 並且把**哪幾個 case 的綠燈是假的**講明白——這比多一個小數點的通過率有用得多。

### 階段二:品質基線(建立在噪音之上)

```bash
python eval/run_baseline.py --classify-from eval/baselines/<階段一的目錄> \
                           --compare      eval/baselines/<要比的基準>
```

只有分級完成後,品質數字才有意義:穩定案例貢獻可靠的 pass/fail;
邊界與不穩案例貢獻分布。**回歸門檻由階段一量到的噪音決定,不是憑感覺訂。**

## 3. 自適應取樣:N 由量到的變異決定

固定 N=3 會同時「浪費在穩定案例上」又「不夠用在不穩案例上」。

| 階段一的分級 | 之後每輪跑幾次 |
|---|---|
| 穩定 | **1** |
| 邊界 | **3** |
| 不穩 | **5**(且不列入評分) |
| 沒有分級記錄 | 當**不穩**處理(寧可多跑,也不要拿沒量過噪音的 case 當閘門) |

以現況估算(假設 20 穩定 / 8 邊界 / 4 不穩):20×1 + 8×3 + 4×5 = **64 次**,
比「32×3 = 96 次」少三分之一,而且把跑批花在真正會晃的地方。

---

## 4. 環境指紋:記錄「實際送出去的」,不是「設定檔寫的」

最痛的教訓是**把設定檔當成事實、卻沒有人去看實際送出去什麼**。兩個例子:
`models.yaml` 宣告 `num_ctx: 32768`,但 `agent.py` 沒送、OpenAI 相容路徑也不吃;
而大家一直以為跑批帶著 `seed`,實際上 `seed` 從來沒有出現在這個檔案裡
(`git log -S seed -- config/models.yaml` 零筆),跑批用的是正式審查那組設定。
所以指紋一律記**實測值**:

| 欄位 | 記什麼 | 為什麼 |
|---|---|---|
| `code` | git SHA、分支、**是否有未 commit 的改動** | dirty 的結果沒有人能重建,不該當共用基準 |
| `deps` | sqlglot / jinja2 / sqlfluff / openai / pymssql 版本 | sqlglot 換版會改變 AST 預掃的命中,那是確定性差異,不記下來會被誤讀成模型變了 |
| `endpoint` | 端點 URL 的**雜湊**(不記原值)+ `/api/version` | 端點換了就不可比;記雜湊是因為 baseline 目錄會進公開 repo,不該帶內部位址 |
| `model` | 名稱 + **digest** | tag 可以被重新指向別的權重,名稱一樣、行為不一樣 |
| `params` | temperature、max_output_tokens(實際送出);`num_ctx_declared` 與 `num_ctx_effective` 兩欄;`seed_effective` | 宣告值與實測值分兩欄,免得下一個人又以為宣告就等於生效 |
| `sandbox` | SQL Server 版本字串 | 方言語意會影響執行驗證的結果 |
| `timing` | 短呼叫耗時中位數與極差 | 判斷計時數據能不能跨輪比較 |

### 規則:指紋不同的兩份 baseline 一律不准互比

`preflight.py --compare` 會逐項比對下列欄位,任一項不同就回離開碼 1:

```
model.digest / endpoint.url / endpoint.api_version
params.seed_effective / params.num_ctx_effective
sandbox.engine / deps.sqlglot / deps.jinja2
```

**刻意不比 `code.sha`** —— 程式碼改變正是回歸比較要量的東西,
把它列進來等於永遠不能比。

## 5. 起飛前檢查:性價比最高的一步

```bash
python eval/preflight.py --offline   # 只做確定性檢查,秒級,可掛 CI
python eval/preflight.py --quick     # 加端點/模型/沙盒,不呼叫模型,數秒
python eval/preflight.py             # 加三個模型探針,約一到三分鐘
```

上一輪在環境失敗上白燒了 4-6 小時(`mr_405` 八次嘗試、`mr_402`、`mr_403`、`mr_406`),
**全部都是兩分鐘內驗得出來的問題。**

| 檢查項 | 方法 | 失敗代表 | 級別 |
|---|---|---|---|
| 程式碼版本 | git SHA + 未 commit 改動 | dirty → 不可當共用基準 | warn |
| 套件版本 | `importlib.metadata` | 缺 pymssql → 執行驗證會整組落在「沙盒不可用」 | fail |
| 端點身分 | `/api/version` + 端點 URL 的雜湊 | 與舊指紋不同 → 換了端點,不可比 | warn |
| 模型 digest | `/api/tags` 比對舊指紋 | 不同 → **不准與舊 baseline 比** | fail |
| 執行驗證沙盒 | 真的跑一正一反兩個案例(建表→灌資料→執行→比對→rollback) | 不可用 → 每個 case 會多一條假的 major | fail |
| `seed` 是否生效 | 同 seed 兩次 **+ 不給 seed 的對照組** | 不生效 → 連單次呼叫都不可重現,整輪只能走分布 | warn |
| context 長度 | 開頭藏隨機 marker、塞到 `budget.diff` 長度、最後問 marker | 記不得 → prompt 正在被靜默截斷 | warn |
| 推論延遲 | 3 次短呼叫的中位數與極差 | 極差 > 3 倍 → 計時數據不可跨輪比 | warn |

兩個檢查的設計值得說明,因為第一次做都做錯過:

**seed 探針一定要有對照組。** 只跑「同 seed 兩次」、兩次一樣就宣告生效是錯的:
prompt 本身在 temperature=1.0 下若沒什麼隨機空間,不給 seed 也會一樣,結論是假陽性。
所以三次呼叫:A、B 同 seed,C 不給 seed。
`A==B 且 C!=A` → 生效;`A!=B` → 不生效;`A==B==C` → **無法判定**(這個 prompt
量不出隨機性,也就量不出 seed 有沒有用)。
另外 `max_tokens` 要給夠(≥800):推理型模型會先燒 token 在內部推理上,
給太小會回空字串,而兩次空字串「相同」又是一次假陽性。

**context 探針要對上 `budget.diff`。** `models.yaml` 宣告 `num_ctx: 32768`,
但 `agent.py` 從來沒把它送出去。**而且就算送了也沒用**:OpenAI 相容路徑本來就不吃
`num_ctx`(放在頂層或放進 `options` 都試過,都不會改變實際 context 長度)——
這個參數是 Ollama 原生 API 的東西。實際的 context 長度由端點自己的預設值決定,
目前是 32,768。所以 `num_ctx` 這一項**不是「我們忘了送」的 bug,而是這條路徑上
根本沒有這個旋鈕**,能做的只有實測目前的長度夠不夠。超長 prompt 是**從開頭被截掉**的,
`build_diff_section` 把 SQL 放前面、指示放後面,所以被截掉的正是受審的 SQL——
模型照樣會產出一份看起來完整的報告,只是它沒看到程式碼,而報告不會說。
所以探針把 marker 放最前面、填充到 `budget.diff` 的長度,最後才問 marker 是什麼。

**任一項 fail 就中止**,不要跑完十幾小時才發現數據不能用。
`run_baseline.py` 預設先跑 preflight,不過就不開跑(`--skip-preflight` 可強制,
但那輪沒有指紋,報告會標明**不可當回歸基準**)。

## 6. 回歸判定規則

| 觀測 | 判定 | 理由 |
|---|---|---|
| **穩定**案例從通過變失敗 | 🔴 回歸,擋下 | 它在同環境下 N 次都一致,翻盤就是訊號 |
| **邊界**案例單次翻盤 | ⚪ 不判定,補跑到 N=3 再看分布 | 單次翻盤是噪音的正常表現 |
| **邊界**案例通過率明顯下降(如 3/3 → 0/3) | 🟡 疑似回歸,人工判讀 | 分布位移才是訊號,不是單點 |
| **不穩**案例任何變化 | ⚪ 只記錄,不判定 | 先修測資生成,它現在量不出品質 |
| 聚合指標超出噪音區間 | 🟡 疑似回歸 | 見下 |
| 指紋不同 | ⚫ 不可比,重建 baseline | 見 §4 |

**噪音區間怎麼來**:取舊 baseline 裡「跑過 2 次以上」的 case 的通過率,算標準差。
量不到就退回 0.05,但那是猜的,報告會標明。**沒有量過噪音就訂門檻等於在猜。**

**硬閘門只放在「穩定案例」與「聚合指標」兩處。** 聚合指標的噪音區間比個別案例小得多,
它超出區間才值得叫人;把紅燈綁在會晃的個別案例上,紅燈就會變成大家習慣忽略的雜訊——
那比沒有紅燈更糟。

### 翻盤 → 先補跑,再判回歸

看到穩定案例翻盤時,**不要立刻宣告回歸**:先對那個 case 自動補跑 2 次
(`--case <id> --runs 2 --no-resume`)。三次裡仍然翻,才判回歸;
只有第一次翻、後兩次回來,記錄為「該 case 的分級需要重新評估」——
它其實不是穩定案例,階段一的 N=5 沒抓到。

## 7. 執行機制:把踩過的坑都內建進去

**① per-case 一個子行程,不是一個行程跑 32 個**
隔離(一個 case 卡死或炸掉不影響前面幾小時的成果)、可續跑、卡死殺得掉。

**② 檔案存在 ≠ 跑成功**
上一輪 `run_percase.sh` 只檢查 `case_<id>.json` 存不存在,結果 4 個
「連不到本機 Ollama:timed out」的錯誤紀錄被計成成功,宣稱 30/32、實際 26/32
(FINDINGS「發現十一」)。`result_ok()` 改成驗內容:JSON 解得開、有這個 case 的那一列、
那一列沒有 `error`、`errors` 清單是空的。

**③ 環境失敗 ≠ 測試失敗**
重試用盡仍拿不到有效結果的 case 列進 `env_failures`,**不計入通過率**,
報告裡獨立一節。把環境問題算成品質退步,是上一輪最大的誤判來源。

**④ 卡死門檻收緊**
實測單次 LLM 呼叫合理上限約 750 秒,原本的預設 3600 秒等於「卡死就等一小時」。
改成子行程 `LLM_TIMEOUT=900`、單 case 牆鐘上限 2400 秒(一個 case 會有主審查 +
測資生成 + 仲裁多次呼叫)、最多嘗試 2 次。

**⑤ 續跑**
已有有效結果的直接跳過(跑批十幾小時,中斷是常態)。`--no-resume` 可強制重跑。

**⑥ 計時落地**
每個 case 每次跑的耗時記進 `summary.json`,子行程的完整輸出留在 `logs/`。
環境劣化才看得出來——上一輪觀測到同一個呼叫 53s → 681s(輸出量相同,差 13 倍),
沒有計時紀錄的話這件事根本發現不了。

**⑦ `--dump-prompts`:驗「管線為什麼不可重現」**
`--dump-prompts` 會把每一次**實際送出的 prompt** 原文寫進
`prompts/<case>_run<n>/` 底下。用途只有一個,但那是 §1 唯一
沒有結論的問題:

```bash
python eval/run_baseline.py --case mr_406 --runs 2 --dump-prompts --tag whynot
diff -ru <baseline>/prompts/mr_406_run1/ <baseline>/prompts/mr_406_run2/
```

判讀:

| diff 結果 | 代表 |
|---|---|
| prompt **相同**、輸出不同 | 是**取樣**——與 §1 查到的「管線沒帶 seed、temperature 是 0.1」一致,把那兩項釘死就會消失 |
| prompt **不同** | 是**輸入**差異,而且 diff 直接指出是哪一段在變(沙盒資料庫名、錯誤訊息、工具輸出的排序),可以逐項消除 |
| **兩者都有** | 最可能的情況。先釘 seed/temperature,再跑一次這個 diff,看還剩多少 |

兩種都是**可以修的**,這正是值得先做這個 diff 的原因:它把「管線為什麼會飄」
從一個統計問題變回一個工程問題。把會變的東西一個一個釘住,噪音會跟著降,
而那比任何取樣手段都根本。

預設關閉——prompt 原文很大,而且含受審的 SQL,不該每輪都留。

## 8. 收集與評分分離:最大的結構性改善

`run_eval.py` 原本把「跑管線」與「算分數」綁在一起,所以**改一條斷言就要重跑 18 小時**,
而且重跑的結果還會飄——飄了就不知道是改壞了還是環境在晃。

```bash
python eval/run_eval.py --dump-reports d/   # 慢(要 GPU):跑管線,完整報告落地
python eval/run_eval.py --from-reports d/   # 快(毫秒):讀存檔重新評分
```

`--from-reports` 的價值不只是快:**輸入完全固定**,所以差異一定來自這次改的斷言
或計分邏輯,不會混進模型的抖動。改 `_golden` 斷言、改 `finding_matches`、
調 rubric 權重——全部都在這條路徑上驗證,不必碰模型。

同一個原則也用在彙總上:`run_baseline.py --summarize-only <dir>` 從落地的結果檔
重建分級與報告,不重跑任何 case。改了分級門檻想重看一次,幾毫秒。

## 9. 配對交錯:評估「某一項改動」時用

要量的是**某個改動**的影響(例如「已有 blocker 時跳過 spec_exec」這種會改變輸出的
加速手段),不是建立新基準時,用配對交錯:

```bash
python eval/run_baseline.py --runs 3 --partner /path/to/other-worktree
```

每個 case 在本工作樹跑完,**緊接著**在另一份工作樹跑同一個 case。

為什麼要交錯而不是先跑完 A 再跑完 B:上游的推論速度與負載會隨時間飄
(實測同一個呼叫 53s → 681s)。先後跑會讓「時間」變成第二個變因,
分不出差異是改動造成的還是環境漂移造成的。交錯之後,漂移對兩邊的影響大致相同,
配對差值才讀得出來。

## 10. 交付物格式

一份 baseline = 一個目錄:

```
eval/baselines/2026-09-18-57c0371-noise/
  fingerprint.yaml              環境指紋 + preflight 結果
  cases/mr_<id>.run<k>.json     每次跑的評分結果(run_eval --json)
  reports/run<k>/mr_<id>.json   每次跑的**完整報告**(供重新評分,見 §8)
  logs/mr_<id>.run<k>.log       子行程完整輸出(含計時)
  summary.json                  分級、通過率、分布、環境失敗、計時

```

「換了環境就不能比」因此是**結構上強制**的(指紋在檔案裡、判定程式會讀),
不靠人記得。

## 11. baseline 不負責什麼

這件事講清楚,才不會有人以為 baseline 綠燈就代表一切正常。專案的測試分三層:

| 層 | 測什麼 | 速度 | 會被什麼推翻 |
|---|---|---|---|
| ① 確定性單元測試 | 注入掃描、後處理鏈、決策閘門、知識衝突、dbt 展開、**評測工具自己的計分邏輯** | 秒級 | 只有邏輯本身改了 → **永久有效** |
| ② 假模型整合測試 | 管線串接:預掃 → 後處理 → 決策三態走得通 | 秒級 | 同上 → **永久有效** |
| ③ golden set(= baseline) | 模型抓不抓得到規格不符、擋不擋得住越獄 | 小時級 | 換模型 / 換環境 / 改 prompt → 要重建 |

①② 是**硬閘門**,每次 push / PR 都跑(`.github/workflows/tests.yml`,715 個測試約 16 秒)。
**③ 不是閘門,是能力量測。**

所以 golden set 該縮回「只問模型才答得出來的問題」:注入類的**偵測**、rule-base 的
規則命中、binding 的確定性抑制、引用白名單的判定,現在都有秒級單元測試覆蓋
(對應關係見 [README.md](README.md) 的 case 表)。對應的 golden case 保留
「端到端有沒有真的變成 blocker、決策落點對不對」的價值,不再用它們覆蓋 pattern
的排列組合。**縮小之後,跑多次才付得起。**

其中一項特別重要:**尺自己要先準。** `finding_matches`、`match_expected`、
`is_style_finding` 是每一條斷言與每一個 recall/precision 數字的必經之路,
它們有 bug 的話 baseline 的每個數字都是錯的,而且不會有任何錯誤訊息。
而且有前例:`allowed_citations` 曾經拿 dict 跟字串比,讓 citations 層永遠不可能通過
(FINDINGS「發現七」)——那個 bug 存在期間,那一層的數字全是假的。
現在 `tests/test_eval_scoring.py` 覆蓋了這三個函式。

## 12. 與 dbt 的關係:不衝突

現有 32 個 case 都是純 T-SQL、不含 Jinja 標記,`is_dbt_template()` 回 False 直接跳過展開
(這件事有測試釘住:`tests/test_real_shape.py`)。所以 dbt 接進管線那天,
**現有 baseline 不會失效**。分工:

- 樣板展開對不對 → `test_dbt_render.py` 拿真的 `dbt compile` 當標準答案逐字比對
- 展開後的 SQL 審得對不對 → golden set 餵**編譯後的 SQL**

兩層不重疊,所以 dbt 怎麼改都不會震動 baseline;真實形狀的 case 是**新增**,不是替換。

**誠實預期**:真實形狀(168 行 dbt 模型 + 跨 4 檔 macro)的數字**大概率比現有
32 個 case 差**。那不是退步,是先前的數字量錯了對象——目前所有品質數字都是在
「12 行手寫片段」上量出來的(中位數 12 行 vs 真實 168 行,實測見 `test_real_shape.py`)。

## 13. 操作流程

**第一次(建立噪音基線,最貴的一次)**

```bash
python eval/preflight.py --out /tmp/fp.yaml        # 先確認環境,兩分鐘
python eval/run_baseline.py --stage1 --runs 5 --tag noise
# → eval/baselines/<日期>-<sha>-noise/REPORT.md 的分級表
```

**之後每次要判斷「我的改動有沒有讓結果變糟」**

```bash
NOISE=eval/baselines/<日期>-<sha>-noise
python eval/run_baseline.py --classify-from $NOISE --compare $NOISE --tag my-change
# 離開碼 0 = 沒有判定為回歸;1 = 有 🔴 或指紋不可比;2 = 跑批本身失敗(環境問題)
```

**只改了斷言或計分邏輯(不必碰模型)**

```bash
python eval/run_eval.py --from-reports $NOISE/reports/run1
```

**改了分級門檻,想重看一次既有結果**

```bash
python eval/run_baseline.py --summarize-only $NOISE
```

**評估某一項會改變輸出的改動(A/B)**

```bash
git worktree add /tmp/ref <改動前的 commit>
python eval/run_baseline.py --runs 3 --partner /tmp/ref --tag paired
```

## 14. 已知限制(寫在這裡,不要讓人自己踩)

1. **還沒有量測模式。** 跑批目前跟正式審查共用同一組設定(`temperature: 0.1`、
   不帶 seed),而正式審查刻意保留隨機性是對的——所以跑批的數字全是抽樣,
   不是「這個系統的值」(§1)。要固定的話得另外加一個**只在跑批時生效**的模式,
   不要去改正式行為。
   而且就算加了也不保證固定:管線是多輪 agent loop,後一輪的輸入含前一輪的
   工具結果,其中有會變的東西。**還剩多少要那時候才量得到**,
   驗法見 §7 的 `--dump-prompts`。
2. **測資生成的覆蓋度會抖**,這是目前最大的噪音來源(`mr_405`/`406`/`408` 三個
   邊界案例都卡在這裡)。修好它的收益比任何統計手段都大。
3. **`num_ctx` 在這條路徑上沒有旋鈕可調**:`agent.py` 沒送它,而 OpenAI 相容路徑
   本來也不吃它(頂層與 `options` 都試過),實際長度由端點預設值決定(目前 32,768)。
   所以長輸入有被靜默截斷的風險而我們調不動,preflight 的 context 探針只能告訴你
   「現在這個長度安不安全」。
4. **一輪仍然很久。** 99.95% 的牆鐘時間是等 LLM(確定性層加起來不到一秒:
   MS SQL 沙盒 0.4s、方言轉換次秒級)。收集/評分分離(§8)與縮小 golden set(§11)
   把「改斷言」從 18 小時降到毫秒,但「重新收集」仍然是小時級——
   那一段要靠環境端的推論速度,不在這份方法書能解決的範圍內。
5. **真實形狀的 case 還建不起來**:`resolve_spec()` 已經實作了「規格依檔名對應」,
   但還沒接進 `spec_exec.find_spec`(issue #7 的工作)。接線前,
   `mrt_RETAIL_M1.sql` 這種沒有 R 編號的輸入會落到「無規格可驗」。
