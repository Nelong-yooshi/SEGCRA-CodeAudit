# R-520 出入帳總額比異常

> 格式依 `examples/sample/RETAIL_M1_spec.md` 的骨架整理,並補上執行驗證所需的
> **資料表定義**段。本規則專門涵蓋**比率型指標**的邊界:除零與進位——
> 這正是範本「待補」段點名、實務上最容易各自解讀的地方。
>
> ⚠️ 合成資料:表名、欄位、代碼、金額門檻皆為虛構,僅供評測使用。

## 基本資料

| 欄位 | 值 |
|---|---|
| 序號 / 程式名稱 | SAMPLE04 / R-520 |
| 資料取用 | txn_log |
| 是否執行加分模組 | 否 |

| 程式負責人 | 資料工程團隊 |

## 說明

計算單一帳戶當日「出帳總額 ÷ 入帳總額」之比率,比率介於 1.00–1.50 者
列入異常清單,於次日批次通報。

## 資料表定義(釘死 schema;執行驗證以此建表)

```sql
CREATE TABLE txn_log(
  account_id INT, tx_time TIMESTAMP, op_code VARCHAR, amount DECIMAL(14,2),
  cash_flag VARCHAR, rev_flag VARCHAR, channel_name VARCHAR);
```

## 排除資料

- **沖銷交易**:`rev_flag = 'Y'` 者不列計。

## op_code 分類

- **入帳 op_code**:`OP01`、`OP02`、`OP03`。
- **出帳 op_code**:`OP21`、`OP22`、`OP23`。

## 篩選條件(逐條可對測資判 true/false)

1. **入帳總額**:`SUM(amount) WHERE op_code IN ('OP01','OP02','OP03')`
2. **出帳總額**:`SUM(amount) WHERE op_code IN ('OP21','OP22','OP23')`
3. **除零處理**:**入帳總額為 0 時,比率一律取 0**(不得為 NULL、不得整筆排除、
   不得除以 0)——取 0 後必然不落在 1.00–1.50,故該帳戶不通報。
4. **進位**:比率**四捨五入至小數第 2 位後**再與門檻比較
   (例:1.004 → 1.00 通報;0.996 → 1.00 通報)。
5. **閾值**:比率 **介於 1.00–1.50**(含兩端,`>= 1.00 AND <= 1.50`)
6. **時間窗**:交易日整日,採半開區間
   (`tx_time >= :start_date AND tx_time < :end_date`)
7. **通報粒度**:每帳戶每交易日至多輸出 1 筆
8. **輸出欄位**:`account_id`、比率(`ratio`)

## 待補(核定規格未載明,不從程式碼腦補)

- **出帳總額為 0 但入帳不為 0**:比率為 0,規格未特別載明,依第 5 條自然不通報。
- **負數金額**:規格未載是否可能出現負數金額(如更正交易)。

## 補充

- 第 3、4 條是本規則的重點:除零與進位在核定規格中**已明確定義**,
  實作若各自解讀(分母 0 時回 NULL、或不做四捨五入直接比大小),
  結果會與規格不符,邊界測資會抓到。
- 「介於」含兩端;恰 1.00 與恰 1.50 **應**通報。
